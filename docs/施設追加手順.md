# チャットから施設を追加する手順

## 構造と不変条件

- 入力: `data/` 直下の小文字拡張子 `.csv`。UTF-8（BOM可）またはCP932。列別名・独自列・複数行セルは `tools/build-data.py` の `read_csv` が解釈する。
- 資料管理: `data/material-registry.json`。`id` は資料固有の永続キー、`number` は画面表示用の連番。生成時に現存CSVの順序をregistryへ反映し、削除・統合後はnumberを1から詰める。作業開始時にユーザー指定の資料番号と資料名・CSVを必ず照合する。
- 出力: `generated/facility-data.json` と `.js`、schemaVersion 2。`index.html` はこのJSを読み、`script.js` が表示する。施設リンクは資料ID＋行位置なので途中挿入・ソートは禁止。
- ルートの `facility-data.*`、`material-registry.json`、`facilities.js`、`facility-catalog.js` と `backup/` は旧データ。更新対象にしない。
- 実行されるCIは `.github/workflows/build-data.yml`。`workflows/build-data.yml` は参照用コピーなのでワークフロー変更時は同期する。CIはテスト→生成→既定ブランチで生成物commit→Pages公開。PRでは公開しない。CIのテストは生成前なので、必ずローカルで生成・全検証済みのCSVと生成物を同じcommitで送る。構文検査・追加保全検証は下記のローカル手順で実施する。

## 1. 開始状態と最新main

`git status --short`、`git diff`、`git diff --cached`、現在ブランチ、`git remote -v` を確認。既存変更と未追跡ファイルの一覧を記録する。元から存在する変更を自分のcommitへ混ぜない。`git fetch origin main` で最新を取得する。

mainが最新で作業ツリーに無関係な追跡済み変更がなければそこで作業する。遅れているだけなら `git merge --ff-only origin/main`。他の作業・commit・ブランチがある場合は `origin/main` から一時worktreeと作業ブランチを作り、元の作業領域を保護する。無関係なローカルcommitをmainへ送らない。

作業開始commitのSHAを `git rev-parse HEAD` で記録し、以下では `BASE` と呼ぶ（実際のSHAに置換）。生成前のデータを基準に保全検証するため、commit後も同じSHAを使う。追加前にも生成・既存テストを実行し、既存の問題か今回の問題か区別する。

## 2. 調査と追加先決定

依頼の資料名に対応する既存CSVを探す。指定がなければ既存分類の最も適切な資料を選択する。新資料の明示依頼または適切な既存資料がない場合は `templates/新しい資料.csv` を元に `data/資料名.csv` を作る。番号は手入力しない。

施設名、都道府県、市区町村、公式URLを公式情報などで確認する。閉館・移転や支店の違いを調べ、断定できない内容を捏造しない。説明は資料の趣旨に合わせる。資料の趣旨上必要な閉館施設等はその状態を明記する。曖昧な候補は保留し、確定分を進め、最終報告に理由を残す。

### 関連リンクの必須確認

URLを推測して作らない。検索結果に表示されたURLを、そのまま登録しない。登録前にURLへ実際にアクセスし、2xxで取得できること、404・410・接続不能・削除済みでないこと、リダイレクト後も同じ目的のページが表示されることを確認する。トップページなどへ転送されて目的の情報がない場合は不採用にする。

取得したページのタイトルと本文を読み、対象施設名、所在地、掲載店舗、または資料の目的に直接関係する内容があるか確認する。検索結果のスニペット、URLの文字列、ドメインの信頼性だけでは採用しない。PDFも実際にダウンロードし、PDFとして開けることと対象施設に関係する本文・表・図が含まれることを確認する。確認できないリンクはタイトルとURLを両方空欄にする。

「公式サイト」欄は施設自身または自治体等による公式案内ページ、「関連リンク」欄は公式サイトとは別の文化財資料・地域史・産業史・調査報告等に限る。公式サイトと同一URL、URL正規化後に同一となるURL、リダイレクト後に同一ページとなるURL、施設案内の重複ページは関連リンクに登録しない。機械検査は次で行う。

関連リンクは公的機関の資料だけに限定しない。個人ブログ・個人サイト・訪問記・旅行記・写真記録・note・地域ブログ・専門家の調査ページも、実際の訪問観察、展示物の具体的記述、館内外の写真、地域文化の独自調査など公式サイトにない情報があれば積極的に採用候補とする。施設情報の転載だけ、広告主体、本文の薄いSEO記事、生成AIの量産記事は採用しない。

HTMLリンクの取得・リダイレクト・タイトル/本文照合は次で自動検証する。ネットワークエラーや本文不一致で失敗したリンクはCSVから削除して再検証する。

```sh
python3 -B tools/check-links.py data/資料名.csv
python3 -B tools/check-links.py data/資料名.csv --check-official-overlap
```

この検証はPDFの取得可否とPDF実体までは自動確認するが、PDF本文の対象性は自動抽出に依存せず、必ず人が開いて確認する。PDF本文を確認できない環境ではリンクを登録しない。

## 3. 追加前の重複確認

候補だけのCSVを `/tmp` 等の `data/` 外に作り、既存と同じ列名で記入する。次を実行する。

```sh
python3 -B tools/check-additions.py duplicates /tmp/候補.csv
```

終了コード0は機械的候補なし、2は要照合候補あり、1は入力等のエラー。候補が出ても「テスト失敗」と扱って回避しない。全資料および候補内について、NFKC・空白・大小文字を吸収した同名、部分一致、同一公式URL・地図URLを表示する。出力のrowは見出しと空行を除く施設位置（1始まり）。共有URLは必ずしも同一施設ではない。

機械検出は別名・旧称を完全には判別できないため、全CSVの所在地・公式ページ・旧称も検索して照合する。同一施設の単純な再追加はスキップ。異なる支店や同名別施設は所在地で区別。別資料への意図的な重複収録はユーザーの依頼の趣旨に必要な場合だけ行い、最終報告に理由を記す。元からある重複はそのまま残す。全件既存なら変更や空commitをせず結果を報告する。

## 4. 必要なCSVだけ追記

Pythonの `csv` を使用し、既存列順・文字コード・BOM・改行コードを保って末尾へ追加する。未改行の最終行があるときは行区切りを入れて追記する。全体の再整形や施設の並べ替えをしない。独自列も保持する。既存列で表現できない情報は無理に列を増設しない。

施設名は必須、その他不明な項目は空欄可。地図の空欄は生成時に補完される。評価/rankは廃止済みで使用不可。関連リンクはタイトルとhttp(s) URLの対を最大3件、同一行でURL重複不可。必要なら既存CSVにある列別名に候補を変換する。

macOSでNFC/NFD差により未追跡に見えるファイルは `git ls-files -z` とUnicode正規化で照合する。無関係な未追跡ファイルを取り込まない。元からの未追跡CSVが生成結果に混ざる場合は、追跡済みファイルだけの一時worktreeで作業する。

## 5. 生成・検証・差分レビュー

```sh
python3 -B tools/build-data.py
python3 -B -m unittest discover -s tests -v
python3 -B tools/check-additions.py verify --base BASE
python3 -B tools/check-links.py data/資料名.csv
node --check data.js
node --check script.js
node --check generated/facility-data.js
git diff --check
git diff --stat
git diff -- data/ generated/
```

`verify` は基準commitの全CSV列・全行が先頭から残ること、既存レジストリ全エントリ、全既存施設フィールド・順序・資料番号の維持を検証する。テストはCSVから一時領域へ再生成し実際のJSON/JSと一致することを確認する。固定件数を更新するだけでテストを通すことは禁止。新件数が「元の件数＋実際の追加数」と一致することも確認する。

エラーは原因を修正して生成から再実行。既存データの削除やテストの無効化で回避しない。通常のデータ追加でHTML/CSS/表示コードを変更しない。

## 6. commitとmainへのpush

変更したCSVと、差分のある `data/material-registry.json`、`generated/facility-data.js`、`generated/facility-data.json` のみをパス指定でstageする。作業上必要なツール修正などはその内容をレビューして明示的にstageする。`git diff --cached --check`、`git diff --cached --stat`、`git diff --cached` で無関係な変更がないことを確認し、内容が分かるメッセージでcommitする。

push直前に `git fetch origin main`。リモートが進んでいれば、元のユーザー作業を保護した作業領域で最新main上へ今回のCSV追加だけを適用し直す。CSVの追加順とレジストリ採番が競合し得るので、生成物を手マージせず再生成し、最新mainを新しいBASEとして全検証をやり直す。必要に応じて今回の作業commitのみをrebaseする。無関係な履歴を改変しない。

`git push origin HEAD:main` を実行（forceは禁止）。失敗時は理由を調べ、競合は上記手順で修復して再検証する。認証・通信・ブランチ保護など自動修復できない場合は未完了として明記する。push後に `git ls-remote origin refs/heads/main` と送信commitを照合する。可能ならActions結果も確認し、push成功とPages公開成功を区別して報告する。

最終報告: 追加資料・件数、スキップ/保留と理由、検証結果、commit SHA、mainへのpush結果。完了していない処理を完了と書かない。
